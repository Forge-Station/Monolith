# Repository Guidelines (Monolith / SS14 / RobustToolbox)

Язык общения: исключительно грамотный русский. Не ищи и не создавай файлы `.ts`/`.js` — весь код проекта написан на C# (`.cs`).

## 1. Архитектура проекта
- `Content.Shared` — общая игровая логика, компоненты и сетевые данные.
- `Content.Server` — серверная логика.
- `Content.Client` — клиентская логика и интерфейс.
- `RobustToolbox/` — исходники движка (Git submodule).
- `Resources/` — YAML-прототипы (`Prototypes/`), Fluent-локализация (`Locale/<язык>/`) и ресурсы.
- `Content.Tests/` и `Content.IntegrationTests/` — тесты.
Размещай код по назначению; не дублируй логику, если её можно вынести в `Content.Shared` с клиентскими/серверными расширениями.

## 2. Исследование и достоверность (строго без галлюцинаций)
- Перед изменениями найди ближайшие аналоги в коде. Проверяй реальные сигнатуры API в проекте и подключённой версии `RobustToolbox/`. Не выдумывай методы, события, атрибуты и поля.
- Не делай выводов только по именам типов/методов — проверяй реальную реализацию, перегрузки, вызывающие места и побочные эффекты.
- Разделяй подтверждённые факты из кода и предположения. Если что-то не удалось проверить — прямо укажи это.
- При анализе указывай точные пути, имена типов, методов и номера строк.

## 3. ECS, сетевая синхронизация и ресурсы
- Компоненты хранят состояние, системы (`EntitySystem`) реализуют поведение через `SubscribeLocalEvent<TComponent, TEvent>`. Предпочитай существующие события созданию новых.
- Проверяй жизненный цикл (`Initialize`, `MapInit`, обработчики событий) и сторону выполнения (Client/Server/Shared).
- Для сетевых компонентов проверяй `[NetworkedComponent]`, `[AutoGenerateComponentState]`, `[AutoNetworkedField]` и вызовы `Dirty(...)`. Не добавляй сетевое состояние без необходимости.
- YAML-прототипы размещай в профильных папках `Resources/Prototypes/` по образцу существующих. Пользовательский текст выноси в Fluent-файлы (`Resources/Locale/<язык>/`), не хардкодь строки.

## 4. Стиль C# (`.editorconfig`) и Git
- Кодировка UTF-8, 4 пробела вместо табов, макс. длина строки 120 символов, завершающий перевод строки, без пробелов в конце строк. Не форматируй несвязанные файлы.
- Перед правками учитывай `git status` и незакоммиченные файлы. Не перезаписывай изменения пользователя и не выполняй разрушительные команды (`git reset`, `git clean`, `git checkout`, `git restore`, `git rebase`, `git push --force`) без согласования.
- При багфиксах ищи первопричину и давай минимальное исправление; не подавляй предупреждения анализаторов/nullable.

## 5. Экономия контекста (важно для локальной LLM)
- Исследуй только файлы, прямо относящиеся к задаче (ориентир — до 10–15 релевантных файлов; не читай огромные файлы целиком, если достаточно поиска определений/ссылок).
- Не повторяй поисковые запросы и не перечитывай уже изученные файлы. Прекращай поиск, как только получено достаточно фактов.
- Не запускай сборку и тесты, если задача ограничена анализом кода.

## 6. Сборка и проверки (SDK 10.0.100 из `global.json`)
Перед запуском скриптов проверяй их наличие в `Scripts/bat/` (Windows) или `Scripts/sh/` (Linux). Команды с `--no-build` требуют предварительной сборки:
- Сборка: `dotnet build --configuration DebugOpt --no-restore /p:WarningsAsErrors=nullable /m`
- Модульные тесты: `dotnet test --no-build --configuration DebugOpt Content.Tests/Content.Tests.csproj -- NUnit.ConsoleOut=0`
- Интеграционные тесты: `dotnet test --no-build --configuration DebugOpt Content.IntegrationTests/Content.IntegrationTests.csproj --filter "FullyQualifiedName!~ShipyardTest" -- NUnit.ConsoleOut=0`
- YAML-линтер (без сборки): `dotnet run --project Content.YAMLLinter/Content.YAMLLinter.csproj --no-build`
- YAML-линтер (со сборкой): `dotnet run --project Content.YAMLLinter/Content.YAMLLinter.csproj -c Debug -- NUnit.ConsoleOut=0`

## 7. Формат ответа и работы
- Для сложных задач сначала дай краткий план (архитектура, затрагиваемые файлы, способ проверки) и не начинай правки, если запрошен только анализ/план.
- Не меняй файлы за пределами согласованного объёма. После изменений перечисли затронутые файлы, суть правок и выполненные проверки (или причину, почему проверки не запускались).
