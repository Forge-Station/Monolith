# 03 — обязательные end-to-end тесты на реальном шаттле

## Цель

Не «вызвать событие KIAS», а показать, что **реальные физические/игровые причины** вызывают штатные события движка, затем сенсор KIAS, исполняемую карточку, выход устройства и наблюдаемое изменение мира. Этот gate запускается **до** основной A/B нагрузки. 27 схем — отдельная матрица `04_PRESET_ACCEPTANCE_MATRIX.md`.

## Предварительный запуск

1. Compile/validation KIAS HEAD после патча программатора. Запустить изолированный сервер на Release (UI отдельно с клиентом; автоматические тесты параллельно не запускай во время замеров).
2. Загрузить из `briarKIAS.yml` через штатный `MapLoaderSystem.TryLoadGrid` / соответствующую актуальную map API. Создать отдельную карту, вакуум и достаточную зону вокруг; документировать map ID и stable grid label, исходную позицию. Проверить reserialize/load без потерь.
3. Запустить штатные питание/атмосферу/FTL/электросеть; записать, сколько KIAS устройств online, сколько no-power/no-data, ролей, revision topology. 4 racks должны отчитаться о physical cards; проверка 26 имен, исполнения, ошибок компиляции; `quiet` disabled — особый ожидаемый статус.
4. Инициализировать test-only owner, company, crew/transponder (как штатные игровые сущности) и других акторов; проверить доступ к консоли/стойкам/программатору. Без рандомных ботов, не управляемых replay-движком.
5. Для UI: отдельный тестовый программатор (потому что исходный Briar его не содержит) + карточка. Вставить/выбрать 27 presets, отредактировать параметры, переместить ноды, проверить inspector/ports, WRITE vs DRAFT, rename/eject/reinsert, вставку в rack, reset/disable, reload map. Проверить, что временное изменение карточки не затрагивает исходную.

## Наблюдение

На каждую проверку записать **четыре логические ступени**:

| Ступень | Доказательство |
|---|---|
| Game input | акт/физика подтверждены движком (damage, alarm, live FTL, projectile, collision, crew state, etc.) |
| Detector | нужный sensor/event получен, coverage valid, online/power/data |
| Controller | matching graph on real card исполнился, не soft-skipped cooldown/error, выход с каузальным event id |
| Output | реально изменилась целевая entity/свет/звук/запись/электроцепь/ПКО; если внешнее действие — состояние мира / network event |

Каждый тест запиши: `test_id`, `preset_id`, исходный map/UID/stable label, world state hash before/after, event scheduled tick, actual trigger tick, output effect tick, latency, status, diagnostics, screenshots/log pointers. Не делать вывод по наличию сообщения в recorder при отсутствии требуемого physical effect.

## Основные реальные физические сценарии

### Пожар / разгерметизация

Зажигание с горючим материалом в помещении, настоящее распространение/тушение огня, адекватные температурные и газовые значения; `FireAlarm` и `AirAlarm` должны реально перейти в danger, затем normal. Зафиксировать связь с AirSensor, vents/scrubbers через **DeviceList + DeviceNetwork** (DeviceLink alone недостаточен). Проверить интеграцию AirAlarm/FireAlarm; если их нет в исходном Briar, сделать отдельную test-only копию с одним установленным устройством и отметить исходный грид `BLOCKED`.

**Негативные кейсы:** fake manual Trigger без реальной опасности НЕ считается pass; не сработавшее `FireClear` может быть обусловлено отсутствием его physical card.

### Оружие / детекторы / защитная сеть

Стрелять настоящим оружием; реальные projectiles и WorldTransform, локальная и внешняя стрельба; 4 боковых + по одному передний/задний сектор; попадание и промах. Отдельно проверить `KiasDefenceSystem` с реально совместимыми пушками в test-only fixture; если на Briar только несовместимые, штатное `automatic PDC disabled` не переименовывать в баг. Проверить suppression of friendly projectiles, IFF, overlapping target directions и occlusion.

### Контакт / FTL

Настоящий FTL с cooldown/travel/arrival на открытой карте и в coverage другого Horizon, с разными IFF; строго сравнить completion event и фактическое location. Не подменять `FTLCompletedEvent` прямым вызовом. Дополнительные тесты поворота, движения, стыковки, collisions через physics/docking/shuttle APIs.

### Hull/atmos/energy

Настоящее повреждение конструкции обычным выстрелом/ударом, оценка целостности/пожара/герметичности. Потеря электричества через штатные power net / APC; восстановление; DATA cut/reconnect via cable interactions; контроллеры должны не оставаться в false-positive online и не зависать после обрыва. Проверить отсутствие глобального сканирования всей карты без надобности.

### Экипаж

Игроки/разумные сущности с зарегистрированными транспондерами и без них; 0, 1, 3, 4+ в комнате; `Entities` vs `Crew` и исключение животных/обычного мусора; крит/смерть/воскрешение, проникновение, `MedicalHelp` и Mayday с проверкой доступа. Не путать отсутствие биометрического модуля в basic scanner с багом CrewCritical.

### Динамики/свет/адаптер

Реальное звучание, адресный speaker, ALL fan-out 10 динамиков без потери/дублей; cooldown; реальные светильники `ALL Lighting` и `ANY Lighting` при отсутствии group controller. Отключение света должно сохранять endpoint для последующего включения. Проверить DAM adapter на реальном целевом устройстве и обратную телеметрию. Четырёхпозиционные реле не добавлять ради PASS.

## Проверка UI после патча программатора

Десктопный live-client (не только integration `Measure/Arrange`) открыть на 850×500, 1200×720, 1600×900 (либо реально поддерживаемых ближайших разрешениях и масштабе UI): palette/inspector, длинные русские имена, node placement, connections, Signal vs Bool, числовые константы, ANY/ALL/SPECIFIC, room/group, поиск, адаптер, WRITE/discard/eject. Проверять на реальных сохранённых и чистых графах. Снимать screenshots и выводить потенциальную визуальную регрессию в отчёте. Не маскировать визуальный тест отсутствием GUI.

## Не нарушать состояние оригинала

Для разрушительных кейсов каждый тест стартует на **чистой копии исходного грида** или восстанавливает из snapshot полностью; не делать одну 30-минутную лавину пожаров и потом сравнивать неравные состояния. Для мануальных UI проверок — отдельная карта. Снимки хешируются.

## Значения статусов

- `PASS` — все требуемые ступени подтверждены доказательствами.
- `FAIL` — проверка выполнена, но не соответствует спецификации.
- `BLOCKED` — отсутствующий класс устройств, неполный грид, невозможность создать физическую причину без внесения неразрешённых изменений, компиляция не прошла.
- `INCONCLUSIVE` — неопределённая физика/отсутствие пригодных логов, повторить.
- `NOT_APPLICABLE` — только при формально документированном исключении, не считать PASS.

Если gate не PASS по ключевым профилям — отчёт об остановке FULL 20min A/B и список минимальных правок; отдельный ограниченный диагностический прогон допускается с ярлыком `PARTIAL_COVERAGE`, но запрещено выдавать его за итоговый честный тест.
